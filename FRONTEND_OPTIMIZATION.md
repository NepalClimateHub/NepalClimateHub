### ImageKit workflow verification (read-only, 2026-09-28)

- `src/utils/optimizeImageUrl.ts` is the repository's only ImageKit-specific workflow: it inserts `tr:w-<width>,q-75,f-auto` into URLs whose host is `ik.imagekit.io`, and returns all other URLs unchanged. Existing components and content use ImageKit URLs and transforms, so ImageKit is the project-standard delivery/optimization target in the current codebase.
- No ImageKit SDK/dependency, upload/rehosting script, media manifest, ImageKit credential key, or API/dashboard integration is present in the repository. The repository can transform URLs for assets already uploaded to ImageKit, but it cannot create ImageKit assets itself.
- The seven homepage i.ibb records are referenced only by URL in `featuredActivists.json` and `organizations.json`. The inspected records contain no ownership, license, source, credit, or attribution fields. Repository evidence therefore does not establish that these assets may be copied or re-encoded; permission and any required attribution must be confirmed before migration.
- To proceed, an authorized asset owner/account administrator must provide approved source files (or confirm permission to use the existing originals), upload them to the project's ImageKit account/media library via the dashboard or Upload API (requiring external account/API access), and return the resulting ImageKit paths. Only then can the relevant data URLs be changed and measured. This cannot be completed entirely within the repository.
- Decision: the existing ImageKit URL-transform workflow is sufficient for delivery after upload, but not sufficient to authorize or perform this rehosting. Keep the seven i.ibb URLs unchanged until ownership/attribution and ImageKit access are confirmed.

## Known limitations

- Resource Timing for `i.ibb.co` is opaque in this browser environment and reports zero transfer/encoded bytes; zero is not interpreted as zero network cost.
- Lazy image loading is distance-threshold based, so “initial” and “post-scroll” can both include the same image request at a 1280×900 viewport.
- The BlogCard after-capture was reproducible on desktop; the follow-up mobile CDP DOM capture did not return usable output, so mobile behavior remains a validation follow-up rather than measured evidence.
- `npm run build` currently prompts for missing `@astrojs/check`/TypeScript and fails without installing dependencies. `npx --no-install astro build` succeeds and is the available production-build check.
- No automated test script exists.
